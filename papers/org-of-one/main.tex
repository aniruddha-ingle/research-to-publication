\begin{abstract}
One software engineer ran a small software organisation for five and a half days in which % ev: derived.json org_span_hours (133.1 h)
almost all of the work was done by concurrent large language model (LLM) sessions on a
single laptop. Each of eight departments is one git repository with one or more Claude % ev: scale.json org.repos
``lead'' sessions. The leads coordinate only through files: a plan-first feature graph in
git with \code{touches} globs, atomic \code{mkdir} claims, one locked integration script,
reviewer agents that never edit, and a gateway session that carries the human's direction
but never his approval. The committed history holds 1,750 commits and 425 merges, 93\% of % ev: scale.json org.commits, org.merges; derived.json org_coauthor_share (0.934)
the commits with a Claude co-author line. Up to five studio leads were active at once, if % ev: leads.json repos.studio.concurrency_from_spans.max_overlap
a session is taken to span its first to last attributed commit. Of the studio's 351 % ev: integrations.json repos.studio.merges
merges, 51 needed a hand resolution, 33 of them on the board file. We code % ev: integrations.json repos.studio.merges_needing_hand_resolution_remerge_diff; hand_resolved_merges_touching_class all 61 dated lessons in the eight lead playbooks into 46 % ev: incidents.json counts.dated_lessons, distinct_events_or_rules
distinct events, 33 of them incidents in ten cause classes, each of which produced a rule % ev: incidents.json counts.distinct_by_kind.incident; distinct_incidents_by_cause_class (10 keys)
written back into a repository. This is an observational case study plus one small
trial, not a controlled experiment. Nothing was recorded that could support a claim
about speed, productivity or cost, and we make none.
\end{abstract}

\section{Introduction}\label{sec:intro}

LLM coding agents can now carry a feature from a plan to a merged branch with little help.
Practitioners already run many sessions in parallel, each in its own git worktree, with a
human as the orchestrator~\citep{mason2026agents}. Research on multi-agent software
engineering has mostly studied role pipelines on benchmark
tasks~\citep{hong2023metagpt,qian2024chatdev,he2024llmmas} or controlled runs of agent
teams~\citep{destefanis2026coordinate}. Less is written down about one person running
such a system for real, for days, on real products, on one machine.

This report describes one such system. The author is a software engineer with a day job.
Over five and a half days (26 September to 2 October 2026) he steered a small % ev: scale.json org.first_commit, org.last_commit; derived.json org_span_hours
organisation whose staff were Claude sessions: a review app for an audio-analysis engine,
the engine itself, three advertising and design departments working for one client, a
department that turns the organisation's research into papers (this is its first), and
a gateway that relays the human's steering. Each department is one git repository. In
each, one or more \emph{lead} sessions plan, dispatch builder and reviewer agents, and
integrate the work. All of them share one Intel laptop and coordinate only through git
and a few files on that laptop. We ask where such leads conflict, what goes wrong when
many sessions share one machine and one human, and how the human keeps authority.

\paragraph{Contributions.}
\begin{itemize}
  \item A documented instance of a git-native coordination design for concurrent LLM lead
    sessions, assembled from standard parts (declared write sets, filesystem locks, a
    local merge queue) plus reviewers that never edit, deployment of \emph{built} work,
    kits that bootstrap new departments, and a written split between \emph{direction}
    and \emph{approval} (\S\ref{sec:design}). We do not claim the parts are new; we
    describe how they behaved together in real use.
  \item Measurements mined from all eight repositories at pinned commits: scale, node
    lifecycles, merge conflicts, and a re-count of the one recorded multi-lead trial,
    after which the department corrected its own record (\S\ref{sec:results}).
  \item A coded set of the 61 dated lessons in the lead playbooks: a cause taxonomy, the % ev: incidents.json counts.dated_lessons
    rule each produced, and how lessons spread (\S\ref{sec:incidents}).
  \item Lessons for practitioners, and what this case cannot show
    (\S\ref{sec:discussion}, \S\ref{sec:threats}).
\end{itemize}
It is an experience report on purpose: there is no baseline, no second machine and no
second human, and the system changed while it ran.

\paragraph{The human.}
The human owns the organisation and makes the taste calls: what is built first, what is
good enough, and what is shown to whom. He works mostly from a phone. Two executives of

\section{Design}\label{sec:design}

The design was planned and built in the studio on 29--30 September (plan 06, ADR 0024; the % source: studio claude-plans/06-multi-lead.md, docs/decisions/0024-multi-lead-orchestration-and-rare-ci.md @af5aaf2
graph landed in \code{16042df}, claims with race tests in \code{df511e9}). The ADR names % source: studio 16042df (2026-09-29 18:20), df511e9 (18:24)
the problem: without a shared record, leads ``collide: two leads pick the same feature,
edit the same files, take the same migration number, or merge into \code{main} at the
same time.'' A personal GitHub account on the free tier has no merge queue and no branch
protection for a private repository, so every gate is enforced locally.
Figure~\ref{fig:arch} shows the parts.

\paragraph{Plan first; a feature graph in git.}
Work starts as a numbered plan and becomes nodes in \code{graph.yaml}, the board. A node
has dependencies, a priority, the agents it needs, a gate size, a state (\code{todo},
\code{claimed}, \code{building}, \code{review}, \code{ready}, \code{merged},
\code{deployed}, \code{dropped}) and \code{touches}: globs for the files it will change.
\code{graph.py ready} offers only nodes whose dependencies are merged and whose
\code{touches} do not overlap a running node, which is the scheduling idea of proactive
conflict avoidance~\citep{kasi2013cassandra} done with globs. Ties are broken by a logged
random pick, because the human's rule is ``never wait on the user''.

\paragraph{Atomic claims.}
Claims, reserved numbers (plans, ADRs, migrations, lead names) and mutexes are
directories in a gitignored state directory: \code{mkdir} claims, \code{rmdir} releases
(macOS has no \code{flock}). A lead claims a node before dispatching any agent.

\paragraph{One locked integration gate.}
\code{integrate.sh} is the only way into trunk. Under a lock it merges trunk into the
branch, runs the local tests, requires a reviewer's PASS marker where the node's gate
needs one, merges with \code{--no-ff}, marks the node \code{merged} and releases its
claims. If merging trunk into the branch conflicts, it stops, and a lead resolves the
conflict on the branch.

\paragraph{Reviewers that never edit.}
Each department has a reviewer agent that reads, runs and judges but never changes the
code. Only Blocker and Major findings block. Small nodes take a light gate (the lead's own
look at screenshots); larger ones need the reviewer's PASS.

\paragraph{Deploy at built.}
The human asked for ``the latest unstable running even though PRs might be waiting to be % source: studio plan 06 section 10 @af5aaf2 (the user, 2026-09-29)
merged to main, because I cannot merge on my phone but I can enjoy the latest features
once built.'' The live app runs from its own checkout as \code{main} plus every node at
\code{built}, rebuilt after a quiet window, a verified backup and a health check.
Migrations go live only through \code{main}; rollback is one command.

\paragraph{Rare CI and a pre-push hook.}
Full suites run on GitHub only at rare checkpoints, to stay in the free tier. A local
pre-push hook refuses audio, data, large files, secret-shaped lines and unsanctioned
pushes to \code{main}.

\paragraph{Playbooks, lessons and kits.}
Each department's lead loads a playbook at every cold start. Its \emph{Lessons} section
is a dated list: when something goes wrong, the fix is made and a rule is written there,
so the next session starts with it. A new department starts from a kit: the playbook
pattern, agents, board and \code{scripts/lead/}. The studio committed four kit handoffs; % ev: structure.json (studio claude-plans/handoffs: 4)
at the pins the full kit is in six repositories. % ev: structure.json repos_with_lead_kit

\paragraph{Direction is not approval.}\label{sec:governance}
The gateway's committed rules state the split: ``Relay is not permission. The gateway % source: gateway CLAUDE.md @a9a58bd, "Rules" (scrubbed: named people replaced by a bracketed role)
carries direction (goals, priorities, deadlines, cross-department calls). It never relays
approval for spend, deletes, exposing anything outside the tailnet, the people gate (what
[the executives or the client's owner] see) or a permission prompt.'' Those go to the
human, who answers in the lead's own session. The organisation-wide rules file that every % source: org-root CLAUDE.md (not under version control); research-to-publication CLAUDE.md "Direction" @887dd2c
session loads states the same split (it is not under version control), as do this
department's committed rules. The gateway adds: ``never ask a lead to do something this session couldn't do itself
(no permission laundering).''

\section{Data and method}\label{sec:method}

\paragraph{Mining.}
A script makes bare clones of the eight repositories and reads their history at pinned
commits (Appendix~\ref{app:repro}). It runs only git, runs none of the departments' code
and writes nothing in their repositories; re-running it gives byte-identical output.
Dates are committer dates in US Eastern time; author and committer dates differ in 17 of % ev: README.md "Environment and commands" (17 of 1,750)
1,750 commits.

\paragraph{Lifecycles and merges.}
Every commit that changed a board is parsed and diffed against its first parent; a node's
time in a state is the first commit showing it there. Node ids are replaced by neutral
ids, since some name the client or a song. A merge \emph{needed a hand resolution} if
\code{git show --remerge-diff} is non-empty, i.e.\ an automatic re-merge would differ.
This is stricter than searching commit messages, which mention a conflict in 43 studio % ev: integrations.json repos.studio.merges_whose_message_mentions_a_conflict
merges.

\paragraph{Lead sessions.}
Only the studio names its sessions in commit subjects. A commit is attributed to a lead
only if a parenthetical in its subject starts with exactly one lead name, which covers 221 % ev: README.md "Lead sessions" (221 of 1,355, 16.3%)
of 1,355 studio commits (16\%). A lead is taken to be active from its first to its last
attributed commit. That span includes idle time, and a lead that never names itself is
invisible, so the concurrency estimate can be wrong either way.

\paragraph{Lessons.}
Each of the 61 dated lessons was coded once, by a Claude session acting as this % ev: incidents.json counts.dated_lessons
department's reproducer: kind (incident, practice or the human's directive), one of eleven
cause classes, harm, fix, rule, and the commit that added it. Copies into another
repository, and second lessons about the same event, link to the original. A script
checks coverage, dates, sources and that nobody is named. There was one coder.

\paragraph{Committed versus observational.}
A few numbers come from the studio's \emph{uncommitted} state directory and deploy logs,
read read-only with the studio's agreement: PASS markers, number reservations and deploy
logs. They are a snapshot that the studio rewrites as it runs, not history, and are
marked \obs{}.

\paragraph{Withheld.}
No client data, product names, measurements, media, audio, track names, session
transcripts, reviewer screenshots, commit subjects or e-mail addresses appear here or in
the evidence files. People are described by role.

\section{Discussion}\label{sec:discussion}

\paragraph{What held.}
Several leads shared one repository for days. Conflicts concentrated on the board file
rather than on code; the trial had no number or deploy collision, and none of the coded
lessons describes one. Every coded incident ends in a rule written back. None of
this shows the design is better than an alternative; it shows it held together under
real use.

\paragraph{Lessons for practitioners.}
\begin{itemize}
  \item \emph{The board is the hot spot.} If coordination state lives in git, change it
    only on trunk, under the lock, and set and commit it in one step.
  \item \emph{Schedule by declared file sets} and let the gate stop, not resolve; then
    resolve on the branch, where a mistake is caught before trunk (usually: see
    studio-16 and studio-17).
  \item \emph{Budget the machine.} A load cap, a heavy-job lock and ``check the load
    first'' were the most-copied rules.
  \item \emph{Plan for sessions to die}: commit work in progress, keep claims and
    worktrees discoverable, hand off before the context runs out.
  \item \emph{Review what the user will see, as the user will see it}: real background,
    real scale, real data.
  \item \emph{Write the lesson where the next session reads it}; kits carry it on.
\end{itemize}

\paragraph{Direction is not approval.}
The split was tested once on record. When the human's grant of autonomy was relayed from % ev: incidents.json gateway-1 (practice)
another session, leads refused to act on it until the human confirmed it in their own
sessions, which was correct (gateway-1). A relay may change \emph{what} a lead works on,
never \emph{what it may do}, so no chain of sessions can launder a permission none of them
holds. This is close to treating autonomy as a design decision separate from
capability~\citep{feng2025levels}, applied here to delegation between agents.

\paragraph{The record was corrected.}
The trial record said more than the history supports. After our re-count the studio
added a dated correction under the original sentence instead of rewriting it
(\code{7870aca}). Committed, dated records can be audited and fixed in place, and that is
what made this study possible.

\paragraph{What may generalise.}
The design needs only git, directories as locks, a YAML board and shell scripts. The
failure classes (shared-machine contention, dying sessions, coordination state in git)
should appear wherever several agents share one machine and one repository. The scale
(one human, one laptop, under a week), the taste for speed over caution (unreviewed work
on the human's phone) and the products may not generalise.

\section{Related work}\label{sec:related}

\paragraph{Multi-agent LLM systems for software.}
MetaGPT~\citep{hong2023metagpt} and ChatDev~\citep{qian2024chatdev} arrange agents into
roles that follow a software process and evaluate them on generated tasks; He et
al.~\citep{he2024llmmas} survey the area. SWE-agent~\citep{yang2024sweagent} studies the
interface one agent needs to work in a repository. Our system has roles too, but the unit
of study is a live organisation over days, not a run on a task.

\paragraph{Coordination of agent teams.}
Two studies are closest to the design. EvoGit~\citep{huang2025evogit} also coordinates
agents only through git, but in the opposite way: there is no trunk, no lock and no task
board; each agent branches from a frontier of versions, versions are combined by a
three-way ``crossover'' with randomised conflict resolution, a version is kept if it
improves on its parents, and a human prunes branches every 10--20 iterations. Our leads
instead serialise every change into one trunk through a locked gate, claim work before
starting it, and leave conflicts to a lead rather than to chance. Destefanis and
Aste~\citep{destefanis2026coordinate} run 1,902 Claude Code team runs on synthetic Python
tasks, varying team size, structure and a \emph{file policy}: whether agents may, must or
must not coordinate through shared files. That policy governs files as a communication
channel; \code{touches} governs which source files a node may write, which is closer to
declared write sets in human teams~\citep{kasi2013cassandra}. Their runs involve no git
and report no merge conflicts, so our main conflict finding, that the shared coordination
file in git is the most conflicted file, has no counterpart there; their finding that
mandated files cut tokens on message-heavy work is about a cost we did not measure. Cemri
et al.~\citep{cemri2025mast} derive 14 failure modes from annotated traces of multi-agent
systems; our incidents differ in kind, being mostly about the shared machine, dying
sessions, deployment and the human's gates. De Oliveira et al.~\citep{oliveira2026masexperience}
report on building with open-source multi-agent frameworks for a software engineering
task, and practitioners describe many agents in parallel worktrees under a human
orchestrator~\citep{mason2026agents}.

\paragraph{Mining agent activity in real repositories.}
The closest prior work in method mines what coding agents leave in real repositories. The
AIDev dataset~\citep{li2025aiteammates,li2026aidev} collects hundreds of thousands of
agent-authored pull requests from five agents across tens of thousands of GitHub
repositories, and Watanabe et al.~\citep{watanabe2025agentic} study 567 Claude Code pull
requests in 157 open-source projects, of which most were merged. Both treat the agent as a
contributor to a human-run project and measure outcomes at the pull request: acceptance,
revisions, review. We mine the opposite case at a much smaller scale: one organisation in
which agents write nearly all commits and also plan, review and integrate, with no pull
requests at all. Our units are board nodes, merges and lessons, so we mine the board's
state history and re-merge every merge (\code{--remerge-diff}) rather than pull request
metadata. The method gives depth on one system and no breadth; it says nothing about how
common such organisations are.

\paragraph{Merge conflicts.}
For human teams, merge conflicts are common and costly: Brindescu et
al.~\citep{brindescu2020merge} link them to later defects, and Nelson et
al.~\citep{nelson2019lifecycle} describe how developers plan for, resolve and avoid them.
Conflicts can be detected early~\citep{brun2011crystal} or avoided by
scheduling~\citep{kasi2013cassandra}; \code{touches} is a crude form of the latter. That
the coordination file is itself the main source of conflicts follows from keeping
coordination state in the same repository.

\paragraph{Incidents and measurement.}
The lessons resemble blameless postmortems, in which each incident yields an action that
prevents a repeat~\citep{lunney2016postmortem}, though far shorter and written by the
sessions themselves. One department measured how a busy shared laptop moves benchmark
results, following Kalibera and Jones~\citep{kalibera2013benchmarking}; that work is not
part of this paper's claims.

\section{Threats to validity}\label{sec:threats}

\paragraph{No speed, productivity or cost claims.}
Nothing recorded the tokens, time or money each session used, and there is no baseline
(one lead, or a human team, on comparable work). We claim nothing about speed-up,
productivity or cost. Commit counts measure activity, not output.

\paragraph{Construct validity.}
Board states are what sessions wrote, and the first commit showing a state stands in for
when it was reached. ``Hand resolution'' also counts deliberate edits made during a merge.
The review-to-merged interval measures integration, not review. Concurrency rests on the
first-to-last-commit span, which counts idle time and misses leads that never named
themselves; outside the studio it cannot be computed.

\paragraph{The lessons.}
Lessons are self-reported by the sessions that had the incidents; an incident nobody
wrote down is missing, and departments differ in how readily they write lessons. One
coder, a Claude session, coded them, with no agreement measure, and the classes are ours.
Lesson dates are as written (UTC), so some differ by a day from the commit adding them.

\paragraph{Observational data and the trial.}
PASS markers, reservations and deploy logs\obs{} were read once from state the studio
rewrites as it runs, and cannot be re-mined. The trial was short (1.26 hours), had three % ev: integrations.json trial_2026_09_30.window_hours
leads for about a minute, and was run by the system's own sessions; its record overstated
the result until corrected. ``0 CI minutes'' is quoted, not reproduced.

\paragraph{External validity and the observer.}
One human, one laptop, one model family, under a week. The organisation changed as it
ran: six of eight repositories are less than a day old at the pins, and rules were added % ev: derived.json repos_first_commit_on_2026_10_02
as incidents happened. The author owns and steered the system, and Claude, which built and
runs most of it, helped mine and write up the evidence. Deriving every number with
committed scripts at pinned commits, having the source department check its own record,
and stating what could not be measured reduce this risk; they do not remove it.

\section{Conclusion}\label{sec:conclusion}

One engineer ran eight departments of concurrent Claude lead sessions on one laptop for
five and a half days, coordinated through git and a handful of files. The history shows
real concurrency in the studio (up to five leads under our span assumption), a board file
that absorbed most of the conflicts, a single locked gate into trunk, and a
steady stream of concrete incidents, each turned into a rule the next session reads. The
most useful rules were about the shared machine, dying sessions and where coordination
state lives, not about the agents' code. Whether the design is faster or cheaper than the
alternatives is open; a controlled comparison with recorded cost is the next study.
